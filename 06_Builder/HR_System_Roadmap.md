# Roadmap: собственная HRIS-платформа уровня Onboardix

**Версия:** 1.0 · **Дата:** 19 мая 2026 · **Автор:** Роман
**Стартовая конфигурация:** полный конкурент Onboardix · vibe-coding с нуля · поток до 20 кандидатов/мес · источники HH.ru (приоритет) + СберПодбор + Avito Работа + Работа.ру

---

## 0. Краткое резюме (TL;DR)

Цель — построить корпоративную HRIS/ERP-платформу, закрывающую полный цикл «заявка на найм → увольнение → alumni» одним кодбейзом. Подход — vibe-coding (1–3 человека + AI-агенты: Claude Code / Cursor / Gemini) с жёсткими архитектурными контрактами, миграциями, тестами и audit-логом.

Реалистичный горизонт при команде 2–3 человека + AI и потоке до 20 кандидатов/мес:

- **MVP «работает найм»** (Phase 0–1) — 8–10 недель.
- **Полный recruiting + offer + onboarding** (Phase 0–4) — 4–5 месяцев.
- **Все 11 модулей в base-функционале** — 12–15 месяцев.
- **Зрелая платформа уровня Onboardix** (с мобильным контуром, partner-контуром, advanced compliance) — 18 месяцев.

Главный риск — рассыпать фокус на 11 модулей сразу. Принцип: каждая фаза заканчивается **рабочим артефактом, который снимает реальную операционную боль**, а не «80% готового модуля».

## 1. Анализ задачи

### Что у конкурента (Onboardix), кратко

11 модулей: (1) Recruiting · (2) Offer + DocuSeal · (3) Onboarding · (4) Lifecycle (12 sub-модулей) · (5) LMS · (6) Performance · (7) Finance/Ops · (8) Analytics · (9) Partner B2B · (10) Compliance/Security · (11) Mobile.

### Что нужно нам прямо сейчас (формулировка пользователя)

«На постоянной основе добывать персонал». То есть **главный KPI Phase 1** — стабильный поток квалифицированных кандидатов в воронку, с минимумом ручной работы рекрутера.

### Что отсюда следует для приоритизации

1. Phase 1 (Recruitment Core) — критический путь, всё остальное — позже.
2. Phase 0 (Foundation) — не пропускаем, иначе через 3 месяца переписываем половину кода.
3. Финансы / LMS / Partner-контур — откладываем до момента, когда найм уже стабильно работает.
4. Мобильный контур (Phase 11) — последним, начинаем с PWA, не с native.

## 2. Принципы vibe-coding с жёсткими контрактами

Это не «нагенерили промптами и забыли». Правила, которые AI-агенты не имеют права нарушать:

- **Архитектурные контракты в репо** — `/docs/contracts/*.md`: схема БД, FSM статусов, API-контракты, разрешённые зависимости. AI читает их в каждой сессии.
- **Миграции — единственный способ менять схему БД.** Никаких ad-hoc `ALTER TABLE` от агента. Tooling: Alembic / Prisma Migrate / Drizzle.
- **Audit log на каждую мутацию** — `who / when / what / why`. Применяется через middleware, а не вручную в хендлерах.
- **RLS на уровне Postgres** — даже если бэкенд ошибётся, БД не отдаст чужие строки. Включаем с первого дня.
- **Тесты обязательны для FSM и денежных операций.** Остальное — best effort, но эти два класса — никогда без тестов.
- **PR-история как ledger.** Каждый PR закрывает одну ясную задачу, с описанием «что» и «зачем». Это и есть «жёсткий контракт» — AI не имеет права смешивать темы в одном PR.
- **Запрет на secret-leak в логи.** Сканер в pre-commit.

## 3. Архитектурный фундамент (Phase 0)

**Срок:** 2–3 недели. **Цель:** на финале — пустая платформа с auth, RBAC, БД, CI/CD, готовая принимать модули.

### 3.1. Стек (рекомендация)

| Слой | Выбор | Почему |
|---|---|---|
| Фронт | Next.js 15 (App Router) + TypeScript + Tailwind + shadcn/ui | Один кодбейз web + PWA; AI-агенты пишут TS лучше, чем что-либо |
| Бэк (API) | Next.js Route Handlers + tRPC | Типобезопасный контракт фронт↔бэк, меньше boilerplate |
| Тяжёлый бэк (парсеры, AI, фоновые) | Python 3.12 (FastAPI) + Celery/RQ | Парсинг HH, нормализация, embeddings — экосистема в Python зрелее |
| БД | PostgreSQL 16 + pgvector | RLS, JSONB для резюме, vector search для дедупликации и RAG |
| Очередь | Redis + RQ (или Celery) | Парсинг, AI-скоринг, рассылки — асинхронно |
| Файлы | S3-совместимое (Yandex Object Storage / MinIO) | Резюме, документы, видео-прокторинга |
| Auth | Auth.js (NextAuth) + WebAuthn для биометрии | OAuth + magic link + биометрия с первого дня |
| Деплой | Docker + Coolify/Dokku на VPS (Selectel/Timeweb) | Railway-style опыт без западных рисков |
| LLM | Gemini 2.5 Pro/Flash через прокси + Claude Sonnet 4.5 (резерв) | Цена/качество для скоринга и RAG |
| E-sign | DocuSeal (self-hosted) | Тот же стек, что у конкурента, открытый код |
| Месснджеры | Telegram Bot API (приоритет) + WhatsApp Business позже | TG — стандарт в RU-найме |

Альтернатива «всё на Python» — реалистична (Django/FastAPI + HTMX или Vue), но front-разработка через AI на TS/React идёт быстрее, и PWA даётся почти бесплатно.

### 3.2. Базовые компоненты Phase 0

1. **Auth + RBAC** — роли: `owner`, `hr_admin`, `recruiter`, `hiring_manager`, `employee`, `candidate`, `partner`. Permissions через CASL или собственный policy-engine.
2. **БД с RLS** — все таблицы имеют `tenant_id` (на будущее multi-tenant) и `org_unit_id`. RLS policies включены.
3. **Audit log** (`audit_events` таблица) — все мутации через middleware. Поля: `actor_id`, `action`, `entity_type`, `entity_id`, `diff`, `ip`, `ts`.
4. **Background jobs** — Redis + воркеры, dashboard (Bull-Board / RQ Dashboard).
5. **Уведомления** — единый сервис `Notifier`: email + Telegram + in-app. Quiet Hours 22:00–09:00 встраиваем в Notifier с первого дня.
6. **Feature flags** — простая таблица + хук, чтобы катить модули за флагом.
7. **CI/CD** — GitHub Actions: lint, typecheck, test, миграции, деплой.
8. **Документ контрактов** — `/docs/contracts/` с описанием FSM, API, схем. Pre-commit проверяет, что новые миграции упомянуты в `CHANGELOG.md`.

**Definition of Done для Phase 0:**
заходим под `owner` → видим пустой dashboard → создаём `hr_admin` → он видит только своё → audit log пишется → деплой одной командой.

## 4. Phase 1 — Recruitment Core (главный фокус)

**Срок:** 8–10 недель после Phase 0 (с учётом sub-phase 1F — транскрибация). **Цель:** через 2.5 месяца команда полностью переводит наём с ручного режима на платформу. KPI — time-to-shortlist падает с дней до часов.

### 4.1. Sub-phase 1A — HH.ru ingestion (1–2 недели)

**Задача:** автоматически тянуть резюме под открытые вакансии в нашу БД.

Шаги:

1. Регистрация работодателя в HH API (если ещё нет), получение OAuth-приложения.
2. Модель `Vacancy` (наш контур) ↔ `hh_vacancy_id` (synced).
3. Sync-воркер: каждые 15 минут тянет отклики по нашим вакансиям через `/negotiations`, кладёт в стейджинг.
4. **Chrome-расширение** для ручного добивания: рекрутер открывает любую карточку резюме в HH-кабинете, жмёт кнопку — резюме улетает в платформу. Это покрывает кейс «нашёл по поиску, не отклик».
5. Нормализатор: HH-формат → наша унифицированная схема `Candidate` + `Resume` (JSONB + индексируемые поля: skills, experience_years, salary_expectation, location, last_active).
6. Anti-duplicate: при загрузке сверяем `email`, `phone`, `hh_id`, fuzzy-match по ФИО + DoB + последнее место работы. Дубль → линкуется к существующей карточке.

**Артефакт фазы:** реальные отклики и резюме за вчерашний день лежат в нашей БД, без участия человека.

### 4.2. Sub-phase 1B — Hiring Requisitions + воронка (1–2 недели)

1. Модель `HiringRequisition`: инициатор, должность, грейд, вилка, обоснование, дедлайн.
2. FSM согласования: `draft → submitted → approved | rejected → in_recruitment → closed`. Цепочка согласующих настраивается per-org-unit.
3. Привязка `Vacancy` к `HiringRequisition` (нельзя открыть вакансию без одобренной заявки).
4. Канбан-воронка кандидатов: колонки настраиваются (`new → screen → tech → final → offer → hired | rejected`).
5. **Дедупликация между вакансиями.** Один кандидат — одна карточка, даже если откликается на 4 вакансии. Просто несколько `Application` записей.
6. Лог стадий — кто двинул, когда, комментарий.

**Артефакт фазы:** руководитель → создаёт заявку → одобряют → вакансия открывается → отклики падают в канбан → рекрутер двигает карточки.

### 4.3. Sub-phase 1C — AI-скоринг резюме (1 неделя)

1. Воркер на каждый новый `Application` строит prompt из job-profile и резюме.
2. Gemini Flash возвращает JSON: `relevance_score (0–100)`, `soft_skills_signals[]`, `red_flags[]`, `values_fit_hypothesis`, `interview_focus_areas[]`.
3. Результат кладётся в `application.ai_scoring` + индексируется. В канбане — цветной бейдж + tooltip с обоснованием.
4. Anti-fraud сигналы из резюме: подозрительные совпадения в формулировках с public-шаблонами, противоречия в датах, нереалистичные сроки на одной должности.
5. **Human-in-the-loop:** скор — это сигнал, не решение. Рекрутер может «не согласиться» — это идёт в reinforcement-датасет для тюнинга промпта.

**Артефакт фазы:** в канбане каждая карточка имеет AI-summary в 4 строки + рекомендуемые зоны для собеседования.

### 4.4. Sub-phase 1D — Автогенерация вопросов и тесты с прокторингом (1–2 недели)

1. Для каждой вакансии — `InterviewTemplate`: набор компетенций, веса, формат (live / async).
2. AI-агент по job-profile + конкретному резюме генерирует **именные** вопросы (`Почему вы 3 года в X пишете на Python, а на Y — Go? Расскажите про переход.`). Это сильно отличается от шаблонных скриптов.
3. **Тесты с прокторингом (Trust Score 0–100):**
   - paste-detection (ловим вставку из ChatGPT),
   - focus-loss tracker (счётчик переключений вкладки),
   - webcam-snapshot каждые N секунд (с согласия 152-ФЗ),
   - keystroke timing — резкие всплески = подозрение на копипаст.
4. Trust Score < 60 → автоматический red-flag в карточке, не блок.
5. Антифрод-симулятор для обучения: рекрутер может прогнать «фейкового кандидата», чтобы откалибровать пороги.

**Артефакт фазы:** кандидат проходит тест по ссылке без логина → результат + Trust Score в карточке → не нужно тащить его на Zoom для базовой проверки.

### 4.5. Sub-phase 1E — Мессенджер с кандидатом + пре-онбординг inbox (1 неделя)

1. Унифицированный inbox в платформе: переписка с кандидатом по email + TG + HH-чат в одной нитке (по `candidate_id`).
2. Шаблоны писем (с переменными), AI-черновики ответов.
3. **Pre-start inbox** — как только кандидат принимает оффер, ему открывается личный кабинет с first-day plan, документами, welcome-видео, FAQ. Снижает «no-show» на старте.
4. Quiet Hours действуют и для исходящих автосообщений кандидату.

**Артефакт фазы:** рекрутер ведёт всю коммуникацию из одного окна, не теряет контекст.

### 4.6. Sub-phase 1F — Транскрибация интервью + сборка оффера из протокола (2 недели)

Конкурент это уже сделал — у нас это критическая фича, потому что устраняет ручной перенос «что обещали кандидату на собеседовании» в оффер.

1. **Интеграция со встречами** — Telemost / Google Meet / Zoom: после звонка в платформу приходит видео + аудио по webhook.
2. **Своё или сторонняя ASR.** Варианты:
   - Whisper (self-hosted, GPU) — дешевле, контроль над данными, согласие 152-ФЗ проще.
   - Yandex SpeechKit — быстрее старт, платно за минуту, ограничения по объёмам.
   - **Рекомендация:** Whisper-large-v3 на собственном GPU-узле или арендованном A10/A100 (Selectel/Immers).
3. **Диаризация** (кто что сказал) — pyannote или WhisperX.
4. **Протокол интервью** — LLM (Gemini) собирает структурированный протокол: вопросы, ответы, ключевые обещания, договорённости по деньгам, дате выхода, специальным условиям.
5. **Связь с карточкой кандидата** — протокол прикрепляется к `Application`, ключевые поля (`agreed_salary`, `agreed_start_date`, `special_conditions[]`) автоматически попадают в драфт оффера в Phase 3.
6. **Quote-link** — в оффере рядом с условием можно нажать «откуда» → откроется фрагмент транскрипта.
7. **Согласие на запись** — обязательное чек-бокс в pre-interview флоу, audit пишется.

**Артефакт фазы:** рекрутер не переписывает руками условия из встречи в оффер — система собирает черновик, человек только проверяет.

### 4.7. Sub-phase 1G — Базовая страница карьеры + лендинги вакансий (3–5 дней)

1. Публичная `/careers` страница — список открытых вакансий из платформы.
2. Лендинг каждой вакансии `/careers/[slug]` — описание + форма отклика (резюме файлом или ссылкой на HH).
3. Форма создаёт `Candidate` + `Application` напрямую, без прохождения через HH.
4. SEO, OG-карточки, шаринг.

**Артефакт фазы:** у компании появляется собственный канал привлечения, независимый от HH-комиссий.

### 4.8. Definition of Done для Phase 1

- За неделю проходит >20 откликов через платформу без ручного копипаста.
- AI-скор + Trust Score сокращают «вручную смотрю каждое резюме» с 100% до <30%.
- Время от отклика до первого ответа кандидату — < 4 рабочих часа в среднем.
- Один human-rejection-rate шаг убран благодаря автоматической отсечке по Trust Score < 30.

## 5. Phase 2 — Multi-source ingestion

**Срок:** 2–3 недели. **После Phase 1.**

Подключаем СберПодбор, Avito Работа, Работа.ру по тому же шаблону, что HH:

1. У кого есть API (Avito — есть API партнёров; СберПодбор — официальный API; Работа.ру — выгрузки) — делаем sync-воркеры.
2. Где API нет/закрыт — добавляем парсинг в Chrome-расширение (тот же UI-флоу, что для HH).
3. Все источники проходят через **один и тот же нормализатор** в схему `Candidate` + `Resume`. Поле `source` хранит origin.
4. **Дедупликация — критична.** Один и тот же человек может быть на 3 площадках. Fuzzy-match + ручной merge с UI «возможно дубль».
5. Дашборд эффективности источников: cost-per-hire, conversion на каждом стейдже.

**Артефакт фазы:** не зависим от ценовой политики HH. Можем перенаправлять бюджет в источник с лучшей конверсией.

## 6. Phase 3 — Offer & DocuSeal (e-signing)

**Срок:** 3–4 недели.

### Что делаем

1. **Конструктор оффера**: шаблон + переменные (имя, должность, грейд, оклад, бонус, дата выхода). Шаблоны версионируются.
2. **Калькулятор зарплаты**: вилка по грейду из job-profile + market-data (если уже подключили HH-аналитику). На выходе — рекомендуемая сумма с обоснованием.
3. **Цепочка согласований оффера**: FSM `draft → manager_approved → hr_approved → finance_approved → sent → signed | declined`. Уведомления в TG.
4. **DocuSeal integration**: self-hosted. Поля автозаполняются из карточки кандидата. После подписания — webhook → платформа меняет статус.
5. **Audit-trail подписания** — кто, когда, IP, чек-сумма документа. Юридическая валидность.
6. Шаблоны оффера для разных типов договоров: ТД, ГПХ, самозанятые.

**Артефакт фазы:** от «принят на оффер» до «подписан с обеих сторон» — без бумаги, без курьеров, аудит-trail готов.

## 7. Phase 4 — Pre-onboarding и Onboarding

**Срок:** 3–4 недели.

1. **Checklist выхода** — шаблон по должности: welcome-email, IT-провижининг (создание аккаунтов Google/Yandex/корп-системы), доступы, оборудование, buddy.
2. **IT-провижининг** — webhook → внешний скрипт создаёт почту/Telegram-доступы. Это интеграционный слой, для каждой компании настраивается своё.
3. **Probation FSM** — `pending → confirmed | extended | not_passed`. Цели на испытательный, автоматические 1:1, чек-поинты.
4. **First-day plan** в pre-start inbox: расписание первой недели, контакты, welcome-pack.
5. **Buddy-программа** — назначение «наставника» из штата, простой UI с задачами для buddy.

**Артефакт фазы:** новый сотрудник на день выхода знает, что ему делать, и у него уже работают все аккаунты.

## 8. Phase 5 — Lifecycle (12 sub-модулей)

**Срок:** 6–8 недель. Можно катить по 1 sub-модулю в неделю — каждый автономен, но они переиспользуют общие сущности (Employee, Goal, OneOnOne, Review).

Sub-модули в порядке value/effort:

1. **Career timeline** — единая шкала событий сотрудника (вышел, перевёлся, повышение, награда, проверка). Просто хорошо построенная агрегация audit-log.
2. **Probation goals** (уже частично в Phase 4) — расширение.
3. **1:1 регулярные** — расписание + шаблон повестки + заметки приватные (manager↔employee).
4. **Manager notes** — приватные заметки руководителя по подчинённому, не видны сотруднику.
5. **Employee voice** — анонимные опросы, NPS, eNPS.
6. **Ask CEO + Town Hall** — публичные вопросы с голосованием, ответы на встречах.
7. **360 Review** — настраиваемые шаблоны, агрегация ответов, AI-резюме (3 параграфа), запрет на reverse-attribution.
8. **Promotion readiness** — матрица: текущий грейд, gap до следующего, чек-лист.
9. **Smart training** (входит во взаимодействие с Phase 6 LMS) — система предлагает курсы по слабым зонам.
10. **Strategic dashboard** — для руководителей подразделений (см. Phase 8).
11. **Exit & alumni** — exit-интервью, off-boarding checklist, alumni-сеть (бывшие сотрудники как реферал-источник).
12. **Internal mobility** — внутренние вакансии видны сотрудникам, отклик в 1 клик, ускоренная воронка.

**Артефакт фазы:** жизненный цикл сотрудника от выхода до увольнения покрыт — данные не разлетаются по 5 системам.

---

## 9. Phase 6 — LMS (Learning Management System)

**Срок:** 5–6 недель.

1. **Learning Paths** — треки, привязанные к должности и модулю. Прогресс по сотруднику.
2. **Тесты** — те же примитивы, что в Phase 1D (прокторинг переиспользуется).
3. **AI-граундинг ответов** — открытые вопросы проверяются Gemini на соответствие эталону + ручная апелляция.
4. **Диалог-тренажёр** — кандидат/сотрудник ведёт диалог с «AI-клиентом» (роль-плей через LLM). Система оценивает скрипт продаж / поддержки / коммуникации.
5. **Spaced Repetition** — повторение по кривой забывания, ежедневные карточки в TG-боте.
6. **Knowledge Hub (RAG)** — корпоративная wiki + поиск по эмбеддингам (pgvector + Gemini-embeddings). Это переиспользуется и в найме (AI-скор «знает» наши требования).

**Артефакт фазы:** обучение перестаёт быть «PDF в Notion» — становится трекаемым, измеряемым процессом.

---

## 10. Phase 7 — Performance Management

**Срок:** 4–5 недель.

1. **360 Review** (уже частично в Phase 5) — углубление: калибровочные сессии руководителей.
2. **IDP** — индивидуальный план развития. Skill-radar текущий vs job-profile целевой → gaps → курсы → дедлайны.
3. **OKR** — квартальные цели, weekly check-in, scoring, дашборд по департаментам.
4. **Manager targets + promo-ready матрица** — каждый руководитель видит «кто из моих готов к повышению через 6 мес».

---

## 11. Phase 8 — Finance & Operations

**Срок:** 5–7 недель. Самая интеграционно-тяжёлая фаза (бухгалтерия, банк).

1. **Expense Management** — заявка → согласование → провод. Валюты RUB, THB, USDT (если работаете в обмен-кейсе).
2. **Compensation калькулятор** — gap-analysis по рынку, plan для повышений.
3. **Табель + расчёт выплат** + отпуска. Интеграция с 1С:ЗУП через выгрузку (XML/CSV) — не пытайтесь делать «полную замену 1С», слишком сложно для команды 2–3 человек.
4. **System Cost Monitoring** — сколько мы тратим на инфру (хостинг, Gemini, TG, DocuSeal). Внутренний учёт по месяцам.
5. **Hardware Assets** — выдача ноутов, лицензий, доступ-карт. История.

---

## 12. Phase 9 — Аналитика и Executive

**Срок:** 3–4 недели.

1. **CEO Dashboard** — high-level: headcount, hiring funnel, retention, payroll.
2. **Dept Head Dashboard** — фокус на отделе.
3. **Manager Dashboard** — на команде.
4. **People Analytics** — burnout-сигналы (private-channel inactivity, переработки в табеле), flight-risk ML на исторических увольнениях, span-of-control, skills footprint.
5. **HR Lifecycle Dashboard** — единая вертикаль метрик: source → application → hire → probation pass → 6mo retention → 12mo retention → exit.
6. **Senate Ops / Exchange Dashboard** — оставляем как опциональные виды на основе тех же мерик.

---

## 13. Phase 10 — Partner B2B контур

**Срок:** 4–6 недель (если действительно нужен).

Если у вас нет B2B-партнёрской сети — пропускаем этот блок и экономим 1–1.5 месяца. Иначе:

1. Реестр партнёров, продуктовый каталог.
2. Импорт партнёрской иерархии (реферальное дерево) из PS2 или другого внешнего ресурса.
3. Quarterly governance, ecosystem partners.
4. Аналитика по партнёрам.

---

## 14. Phase 11 — Compliance и Security

**Срок:** 3–4 недели, частично делается параллельно с Phase 0–10.

1. **152-ФЗ модуль** — согласия (форма + аудит) на обработку ПДн, право на удаление, экспорт «моих данных».
2. **Audit log** (уже из Phase 0) — теперь добавляем экспорт под аудит.
3. **AML-скрининг контрагентов** (если работаете с финтехом) — проверка по санкционным спискам.
4. **RLS** (уже из Phase 0) — закрепляем тесты, что попытка кросс-tenant select падает.
5. **Антиплагиат + антифрод** (уже из Phase 1) — расширяем.
6. **Secret scanning** в CI, ротация ключей раз в 90 дней.
7. **Backup-стратегия** — daily snapshots + weekly off-site + ежеквартальный restore-drill.

## 15. Phase 12 — Mobile контур

**Срок:** 3–5 недель.

1. **PWA** (получается почти бесплатно от Next.js) — Add-to-Home-Screen для iOS, install prompt для Android.
2. **Capacitor APK** для Android-команды — один и тот же JS-бандл, плюс native document-scanner на ML Kit.
3. **WebAuthn + native биометрия** — логин по отпечатку/Face ID.
4. **OTA через Capgo** — катим новый JS-бандл без переустановки.
5. **Дистрибуция** — Telegram-бот раздаёт ссылку на APK + страница `/install`. RuStore / AppStore только если придёт реальная необходимость (внешние пользователи).

## 19. Что отложено сознательно

## Приложение А. Glossary

- **FSM** — finite state machine, конечный автомат статусов сущности.
- **RLS** — row-level security, политики доступа на уровне строк БД.
- **DoD** — definition of done, критерий завершённости фазы.
- **RAG** — retrieval-augmented generation, поиск + генерация на LLM.
- **OTA** — over-the-air обновления (для мобильных).
- **eNPS** — employee net promoter score.
